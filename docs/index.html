OpenChatbox — Handbuch

Vollständige Dokumentation: Installation, Betrieb, Bedienung und Fehlersuche.

v0.10.0 Next.js 16 · App Router Node 20+ Ein Dienst, keine Datenbank

1 · Überblick

OpenChatbox ist eine selbst gehostete Chat-Oberfläche für große Sprachmodelle. Sie läuft als ein einziger Next.js-Dienst und spricht mit einer beliebigen Ollama-Instanz oder einer OpenAI-kompatiblen API. Unterhaltungen und Konfiguration bleiben auf dem eigenen Server.

Ollama ist nicht enthalten. Die Anwendung wird auf einen Endpunkt gerichtet, den du bereits betreibst. Es gibt bewusst keinen mitgelieferten Ollama-Container.

Was die Anwendung kann

  • Antworten streamen — Ollama (NDJSON) und OpenAI-kompatible APIs (SSE) werden serverseitig auf einen Strom normalisiert. „Reasoning“-Ausgabe wird separat dargestellt.
  • Auto-Router: jede Nachricht wird automatisch an das Modell geleitet, das für Programmieren, Reasoning, Bildverständnis oder Allgemeines hinterlegt ist.
  • Wissensdatenbank (RAG): Dokumente (PDF, TXT, MD, CSV, DOCX, PPTX, XLSX) werden lokal zerlegt und eingebettet; Antworten belegen ihre Quellen.
  • BookStack-Anbindung: durchsucht ein BookStack-Wiki und zitiert Seiten.
  • Websuche über einen konfigurierbaren Anbieter — pro Chat standardmäßig aus.
  • Dokumenterzeugung: PDF oder Excel aus einer Antwort.
  • Sidekicks (wiederverwendbare Assistenten-Profile), Workspaces, moderierter Gruppenmodus.
  • Konten mit Ersteinrichtung, optionalem Entra-ID-/OIDC-SSO und optionaler Zwei-Faktor-Authentifizierung.

Voraussetzungen

  • Ein Ollama-Server oder ein OpenAI-kompatibler Endpunkt.
  • Für Docker-Betrieb: Docker und Docker Compose.
  • Für den Betrieb aus dem Quellcode: Node.js 20 oder neuer.

2 · Schnellstart

Variante 1 — Installer (Linux, Docker)

Auf einem Debian- oder Ubuntu-Server mit curl:

curl -fsSL https://raw.githubusercontent.com/bohannjein/OpenChatbox/main/install.sh | bash

Das Skript installiert Docker und Compose falls nötig, klont das Repository, erzeugt eine .env mit AUTH_SECRET und startet den Container im Hintergrund auf Port 6769. Danach http://<server-ip>:6769 öffnen.

Port oder Zielverzeichnis überschreiben:

curl -fsSL https://raw.githubusercontent.com/bohannjein/OpenChatbox/main/install.sh | OPENCHATBOX_PORT=8080 bash

Variante 2 — Docker Compose von Hand

git clone https://github.com/bohannjein/OpenChatbox.git
cd OpenChatbox
cp .env.example .env

# AUTH_SECRET in .env eintragen:
openssl rand -hex 32

OPENCHATBOX_PORT=6769 docker compose up -d --build

Der Container lauscht intern auf 3000; OPENCHATBOX_PORT bestimmt den Port nach außen. Laufzeitdaten liegen im Volume openchatbox-data.

Variante 3 — aus dem Quellcode

npm install
npm run dev                    # http://localhost:3000

# oder produktiv:
npm run build && npm start

Ersteinrichtung

Beim ersten Aufruf erscheint der Einrichtungsbildschirm. Dort wird das Administratorkonto angelegt. Anschließend als Administrator anmelden und unter Einstellungen → Modelle → Anbieter & Endpunkte mindestens einen Modellanbieter eintragen — vorher kann niemand chatten.

Standardzugang ändern. Eine frische Installation legt das Konto administrator mit einem bekannten Standardpasswort an. Das ist ein Erstinbetriebnahme-Zugang, kein Betriebszustand: melde dich sofort an und ändere das Passwort unter Einstellungen → Mein Konto, bevor die Instanz über das Netz erreichbar ist.

Öffentliche App-URL

Die von außen erreichbare Adresse der Instanz. Sie wird an zwei kritischen Stellen gebraucht:

  • Absolute Links in E-Mails — etwa der Passwort-Reset-Link.
  • OIDC redirect_uri — der Wert, den /api/auth/oidc/start an den Identitätsanbieter schickt und den der Callback byteweise identisch erwartet.

Auflösung in dieser Reihenfolge (getPublicBaseUrl()):

  1. Adminfeld Einstellungen → Marke → Öffentliche Adresse
  2. Umgebung: APP_URL → NEXT_PUBLIC_APP_URL → AUTH_URL
  3. Herkunft der Anfrage — als letzter Ausweg
Schritt 3 ist unzuverlässig. Hinter einem Reverse-Proxy oder bei Bindung an 0.0.0.0 entsteht daraus eine unbrauchbare Adresse — E-Mail-Links zeigen ins Leere und SSO scheitert an einer nicht übereinstimmenden redirect_uri. Trage die Adresse in produktiven Installationen immer explizit ein.

Modellanbieter

Unter Einstellungen → Modelle → Anbieter & Endpunkte. API-Schlüssel werden serverseitig verschlüsselt abgelegt und nie an den Browser ausgeliefert.

Ollama auf einem anderen Serverhttp://<host>:11434

4 · Bedienung

Chatten

Nachricht eintippen, Enter senden, Umschalt+Enter für einen Zeilenumbruch. Links neben dem Eingabefeld sitzen drei Schalter:

  • Büroklammer — Dateien anhängen. Bilder und Dokumente werden beim Hochladen geparst und als Kontext übergeben.
  • Globus — Websuche. Eingeschaltet wird der Knopf zu einer beschrifteten Pille „Websuche“; das ist auch die Erklärung, warum eine Antwort länger dauert.
  • Bücherstapel — Wissensdatenbank. Sucht vorab in den hinterlegten Dokumenten und belegt die Antwort mit Quellen.

Über dem Chat wählt der Modellumschalter das Modell; Auto überlässt die Wahl dem Router. Der Schieberegler-Knopf daneben öffnet den Antwortstil — Präzise · Ausgewogen · Kreativ und die Antwortlänge. Die Rohwerte (Temperatur, Top-P, maximale Tokenzahl) liegen darunter unter „Erweitert“.

Nachrichten-Aktionen

Beim Überfahren einer Nachricht erscheinen Kopieren, Bearbeiten (eigene) beziehungsweise Neu generieren, Vorlesen, Bewertung (Antworten) — und der Stern, der die Nachricht markiert.

„Zu diesem Chat“

Das Symbol rechts in der Kopfzeile öffnet ein Panel mit allem, was zum aktuellen Chat gehört:

  • Dateien — hochgeladene und erzeugte Dateien, mit Sprung zur Nachricht und Download.
  • Markiert — die mit Stern versehenen Nachrichten.
  • Notizen — Freitext zu diesem einen Chat.

Davon zu unterscheiden: die chatübergreifenden persönlichen Notizen im Fuß der Seitenleiste.

Inkognito / temporäre Chats

Das Geist-Symbol startet einen temporären Chat: die Oberfläche blendet nach Schwarz, und nichts wird auf dem Server gespeichert. Im Geist-Menü lässt sich der Chat nachträglich behalten (dann wird er normal gespeichert) oder sofort löschen.

Sidekicks & Workspaces

Sidekicks sind gespeicherte Assistenten-Profile mit eigenem Modell und System-Prompt — etwa „Protokollant“ oder „Code-Reviewer“. Mehrere in einem Chat ergeben einen moderierten Gruppenmodus.

Workspaces sind Kollaborationsräume. Chats, Sidekicks und geteilte Dateien gehören zu genau einem Workspace, ein Konto kann in mehreren Mitglied sein. Der Workspace ws-default („Persönlich“) existiert immer; Inhalte ohne Zuordnung fallen automatisch dorthin.

6 · Administration

Benutzer & Rollen

Einstellungen → Benutzer & Zugriff. Konten anlegen, Rollen vergeben, sperren, Passwörter zurücksetzen, löschen. Rollen:

RolleDarf
adminAlles. Implizit Zugriff auf sämtliche Wissens-Kategorien.
poweruserWissens-Kategorien und Dokumente anlegen, hochladen, löschen. Wer eine Kategorie anlegt, bekommt sie automatisch freigeschaltet.
userChatten; Wissens-Kategorien nur lesend und nur die ausdrücklich freigegebenen.

Im selben Bereich liegen Selbstregistrierung (optional auf E-Mail-Domänen begrenzt) und der Gastzugang. Gäste bekommen eine abgespeckte Oberfläche, ein fest vorgegebenes Modell, keine Werkzeuge und rein flüchtige Chats.

Single Sign-On

Einstellungen → Anmeldung & E-Mail → Single Sign-On. Eigener OIDC-Ablauf, kein NextAuth. Beim Identitätsanbieter muss als Umleitungsziel eingetragen sein:

<öffentliche App-URL>/api/auth/oidc/callback

Der Wert muss zeichengenau mit dem übereinstimmen, was die App sendet — siehe Öffentliche App-URL. Ist eine Mandanten-ID gesetzt, wird die Anmeldung zusätzlich auf diesen Mandanten beschränkt. Rollen werden aus dem roles-Anspruch übernommen.

E-Mail-Versand

Einstellungen → Anmeldung & E-Mail → E-Mail-Versand. Nötig für den Self-Service-Passwortreset. Gefordert sind alle folgenden Angaben — fehlt eine, gilt SMTP als nicht konfiguriert:

  • Schalter „aktiviert“
  • Host
  • Port
  • Absenderadresse (ersatzweise der Benutzername)
Der Link „Passwort vergessen?“ auf der Anmeldeseite erscheint nur, wenn SMTP vollständig konfiguriert und die Passwort-Anmeldung aktiv ist. Ohne Versandweg wäre der Link eine Sackgasse, deshalb wird er ausgeblendet statt ins Leere zu führen.

Modelle

Einstellungen → Modelle. Vier Abschnitte:

  • Anbieter & Endpunkte — Basis-URLs und Schlüssel.
  • Modelle laden — Ollama-Pull direkt aus der Oberfläche.
  • Anzeigenamen & Favoriten — Aliasse. Der Alias ersetzt die technische Modell-ID überall in der App; Ein-Klick-Vorschläge bieten Zwecknamen wie „Schnell“ oder „Versteht Bilder“ an. Für Nutzer ohne technischen Hintergrund ist das der Unterschied zwischen einer Auswahl und einem Rätsel.
  • Standardmodelle — welches Modell der Auto-Router je Aufgabe lädt (Programmieren, Reasoning, Bildverständnis, Suchbegriff-Konstruktion …).

Wissensdatenbank

Ein organisationsweiter, gemeinsamer Speicher — nicht pro Konto. Jede Kategorie ist zugleich eine Berechtigung: ein Konto sieht ausschließlich die ihm zugewiesenen Kategorien, Administratoren sehen alle. Die Zuweisung erfolgt über die Kategorie-Matrix in der Benutzerverwaltung. Die Prüfung geschieht serverseitig, bevor irgendein Inhalt in den Kontext gelangt; ohne Zuweisung greift „alles verboten“.

Die Suche läuft gebündelt: lokale Vektorsuche (bereits nach Berechtigung gefiltert) und BookStack werden parallel abgefragt, zusammengeführt, entdoppelt und mit Quellenangabe versehen.

Assistenten & API (Einbetten auf anderen Seiten)

Einstellungen → Administration → Assistenten & API. Ein Assistent ist ein Zugang für fremde Webseiten: festes Modell, eigener System-Prompt und genau die Wissensbereiche, die freigegeben wurden. Ein Assistent ist kein Benutzerkonto — er hat keinen Eintrag in users.json, keine Rolle und kein Sitzungscookie. Damit weisen alle Routen, die ein Konto verlangen, seinen Schlüssel automatisch ab: Chats, Profile und die Verwaltung bleiben verschlossen.

Der Aufrufer wählt nichts aus. Ein im Request mitgeschicktes model wird ignoriert; es gilt das im Assistenten hinterlegte Modell. Ebenso liegen System-Prompt, Wissensumfang und Limits ausschließlich serverseitig.

Schlüssel

ArtPräfixGehört nachSchutz
Geheimocb_sk_in ein fremdes BackendNur dieser Server kennt ihn; keine Herkunftsprüfung nötig.
Widgetocb_pk_in eine WebseiteSteht im Seitenquelltext und ist damit lesbar. Geschützt allein durch die Herkunfts-Liste und das Limit.

Schlüssel werden nur als SHA-256-Hash gespeichert. Der Klartext erscheint genau einmal beim Anlegen — danach nie wieder, auch nicht für Administratoren. Verloren heißt: neuen erzeugen und den alten widerrufen.

Server-zu-Server

Der Endpunkt ist OpenAI-kompatibel, bestehende SDKs funktionieren unverändert:

curl -N https://chat.firma.de/api/v1/chat/completions \
  -H "Authorization: Bearer ocb_sk_…" \
  -H "Content-Type: application/json" \
  -d '{"messages":[{"role":"user","content":"Wie beantrage ich Urlaub?"}],"stream":true}'

Antwort ist text/event-stream mit chat.completion.chunk-Objekten und abschließendem data: [DONE]. Mit "stream": false kommt ein einzelnes chat.completion-Objekt. Zwei Abweichungen von OpenAI: Denkschritte reichen wir als delta.reasoning_content durch, und bei aktivierter Quellenanzeige trägt der letzte Chunk ein zusätzliches x_sources-Feld.

Widget in eine Seite

<script src="https://chat.firma.de/embed.js" data-key="ocb_pk_…" defer></script>

Erzeugt eine Chat-Blase unten rechts (data-position="left" für links). Das Widget läuft vollständig in einem Shadow DOM, sodass sich Seiten-CSS und Widget-CSS nicht in die Quere kommen, und setzt Modellausgaben ausschließlich als Text ein — niemals als HTML.

Die Herkunft muss im Assistenten eingetragen sein, exakt als https://intranet.firma.de (Schema und Host, ohne Pfad). Ohne passenden Eintrag lehnt der Server ab, und der Browser bekommt keine CORS-Freigabe. Ein * gibt es nicht.

Grenzen und Zähler

Je Assistent gelten Anfragen pro Minute, pro Tag und pro Tag und IP, dazu eine maximale Anfragelänge und eine Verlaufstiefe. Bei Überschreitung antwortet der Server mit 429 und Retry-After. Die Zählung liegt im Arbeitsspeicher: nach einem Neustart beginnt das Minutenfenster neu, und bei mehreren Replicas zählt jede für sich.

Gespeichert werden ausschließlich Zähler (Anfragen, Zeichen, Abweisungen, letzte Nutzung) in assistants.json — keine Gesprächsinhalte. Es gibt daher auch keine Aufbewahrungsfrist und kein Löschkonzept für Gesprächsdaten.

Was ein Assistent bewusst nicht kann

Kein Auto-Router, keine OCR-Kette, keine Bild- oder Dokumenterzeugung, keine Datei-Uploads, kein Gedächtnis und keine Wiki-Schreibwerkzeuge. Ein eingebetteter Assistent beantwortet Fragen aus dem freigegebenen Wissen; jede weitere Fähigkeit wäre ein zusätzlicher Weg, im Namen anonymer Besucher Geld auszugeben oder Daten abfließen zu lassen.

Marke (Custom Branding)

Einstellungen → Administration → Marke. Alles Firmenspezifische an einer Stelle: Name, Unterzeile, Logo (mit eigener Variante für helle Oberflächen), Favicon, Akzentfarbe, Impressum-, Datenschutz- und Support-Verweise sowie die öffentliche Adresse.

Der Tab arbeitet mit einem Entwurf: die Vorschau oben zeigt Seitenleiste, Anmeldemaske und Browser-Tab sofort, andere Nutzer sehen die Änderung erst nach Speichern (und dann binnen einer Synchronisationsrunde, ≤ 20 s). Logos werden beim Upload verkleinert und in config.json abgelegt — Transparenz bleibt erhalten, SVG wird unverändert übernommen. „Aus Logo ableiten“ schlägt die Akzentfarbe aus dem Logo vor.

Wo die Marke wirkt: Seitenleiste, Anmelde-, Reset-, Freigabe- und Einrichtungsseite, Browser-Tab und Favicon, Web-App-Manifest, Absender und Layout der Passwort-Reset-E-Mail sowie der Aussteller (Issuer), den Authenticator-Apps bei der Zwei-Faktor-Einrichtung anzeigen.

Für den Rollout auf mehrere Instanzen gibt es drei Wege, die jeweils nur noch nicht gesetzte Felder füllen (die Oberfläche behält also immer das letzte Wort):

  • Export/Import — „Marke exportieren“ erzeugt brand-<name>.json, „Importieren“ liest sie in den Entwurf.
  • Datei — dieselbe JSON als branding.json in das Datenverzeichnis legen, vor dem ersten Start.
  • Umgebung — OPENCHATBOX_BRAND_NAME, _TAGLINE, _ACCENT, _LOGO_URL, _IMPRINT_URL, _PRIVACY_URL, _SUPPORT_EMAIL, _SUPPORT_URL.

Ungültige Eingaben werden verworfen, nicht gespeichert: die Akzentfarbe muss #rrggbb sein, Verweise müssen http(s) sein, Bilder entweder http(s) oder eine Bild-Data-URL bis ~370 kB.

Leistung / VRAM

Einstellungen → Leistung. Steuert, wie schnell Ollama Modelle aus dem Grafikspeicher entlädt — relevant, wenn sich mehrere Nutzer eine GPU teilen. Bei Alleinnutzung ausgeschaltet lassen.

keep_aliveWirkung
2m, 30mNach dieser Zeit ohne Anfrage entladen.
0Sofort nach jeder Antwort entladen. Sparsam, aber jede Anfrage zahlt die Ladezeit.
-1Dauerhaft geladen lassen.

Ergänzend auf dem Ollama-Host: OLLAMA_NUM_PARALLEL=1, OLLAMA_MAX_LOADED_MODELS=1.

7 · Architektur

Ein Next.js-Dienst (App Router). Oberfläche und API-Routen laufen im selben Server; die API-Routen wirken als Backend-for-Frontend gegenüber Ollama, den OpenAI-kompatiblen Endpunkten, BookStack und den Suchanbietern. Client-Zustand liegt in einem Zustand-Store (lib/store.ts).

Es gibt keine laufende Datenbank. Sämtlicher Serverzustand liegt in JSON-Dateien, die atomar geschrieben werden (temporäre Datei, dann Umbenennen). Ein prisma/schema.prisma existiert, ist aber ruhend — ein dokumentiertes Zielmodell, kein zur Laufzeit genutzter Client.

Chat-Synchronisation

Chats sind client-autoritativ. Der Store hält sie und schiebt den gesamten Satz zeitverzögert per PUT /api/chats zum Server, der Persönliches und Workspace-Chats wieder auseinandersortiert.

Für Weiterentwicklung wichtig: keine eigenen REST-Routen für chat-nahe Daten anlegen (etwa POST /api/folders). Der Rundumschlag von PUT /api/chats überschreibt sie. Stattdessen den bestehenden Kanal mitbenutzen und das Chat-Objekt erweitern — so sind Ordner, Chat-Notizen und markierte Nachrichten umgesetzt.

Serverautoritativ sind dagegen die administrative config.json (wirkt über /api/config für alle) und die Profile je Konto.

Anmeldung im Detail

Eigenes, dateigestütztes System — bewusst nicht NextAuth. Sitzungen laufen über ein signiertes Cookie nexus_session mit einem Zweck-Feld (session | 2fa | guest). Die Middleware prüft am Rand nur, ob ein Cookie vorhanden ist — sie hat keinen Dateisystemzugriff. Die eigentliche Prüfung passiert in den Routen; Gast- und 2FA-Cookies liefern dort kein Konto zurück, wodurch jede kontogebundene Route Gäste automatisch abweist.

8 · Betrieb

Update

cd /pfad/zu/OpenChatbox
git pull
docker compose up -d --build

Die laufende Version steht unter Einstellungen → Über OpenChatbox, zusammen mit dem Änderungsverlauf. Das Volume überlebt den Neuaufbau — Konten und Konfiguration bleiben.

Backup

Zu sichern ist genau ein Ort: das Datenverzeichnis.

# Volume sichern
docker run --rm \
  -v openchatbox-data:/data \
  -v "$PWD":/backup \
  alpine tar czf /backup/openchatbox-$(date +%F).tar.gz -C /data .

# Wiederherstellen
docker run --rm \
  -v openchatbox-data:/data \
  -v "$PWD":/backup \
  alpine sh -c "rm -rf /data/* && tar xzf /backup/openchatbox-JJJJ-MM-TT.tar.gz -C /data"

Achtung, Wiederherstellung löscht. Der zweite Befehl leert /data vollständig, bevor er das Archiv auspackt. Stoppe den Container vorher (docker compose stop), prüfe den Archivnamen, und lege im Zweifel erst ein frisches Backup des aktuellen Stands an.

Sichere .env getrennt mit. Geht AUTH_SECRET verloren, sind alle Sitzungen ungültig und alle serverseitig verschlüsselten Geheimnisse (etwa der BookStack-Token) nicht mehr entschlüsselbar.

Logs & Healthcheck

docker compose logs -f openchatbox     # mitlesen
docker compose ps                      # Status inkl. Health
docker compose restart openchatbox     # neu starten

Der Container prüft sich alle 30 Sekunden selbst über GET /api/setup. Diese Route ist öffentlich und liefert JSON — sie eignet sich auch für externe Überwachung.

9 · Troubleshooting

Jeweils Symptom, Ursache, Behebung.

Start & Container

Container startet nicht, Meldung set AUTH_SECRET in .env

Ursache
Compose verlangt die Variable und bricht ohne sie ab.
Behebung
openssl rand -hex 32 ausführen, Ergebnis in .env als AUTH_SECRET= eintragen, docker compose up -d.

Port belegt — address already in use

Ursache
Der äußere Port ist vergeben. Intern ist es immer 3000.
Behebung
OPENCHATBOX_PORT=8080 docker compose up -d oder den Wert in .env setzen.

Container läuft, aber „unhealthy“

Ursache
Der Healthcheck erreicht /api/setup nicht — meist wegen eines Startfehlers im Anwendungscode.
Behebung
docker compose logs --tail=80 openchatbox lesen. Häufig ein unlesbares Datenverzeichnis: Rechte auf dem Volume prüfen, der Prozess läuft als UID 1001.

Anmeldung

Anmeldung wirkt erfolgreich, aber man landet sofort wieder auf der Anmeldeseite

Ursache
Der Browser verwirft das Sitzungscookie, weil es mit Secure gesetzt ist, die Seite aber über einfaches HTTP läuft.
Behebung
AUTH_COOKIE_SECURE=false setzen für HTTP im LAN, true hinter HTTPS. Leer lassen bedeutet automatische Erkennung, die hinter manchen Proxys danebengreift.

Alle Nutzer sind nach einem Neustart abgemeldet

Ursache
AUTH_SECRET ist nicht gesetzt. Die App erzeugt dann ein zufälliges Geheimnis in data/.auth_secret — geht das Verzeichnis verloren oder wird es nicht dauerhaft gespeichert, werden alle Signaturen ungültig.
Behebung
Festes AUTH_SECRET in .env hinterlegen und das Volume dauerhaft einbinden.

„Passwort vergessen?“ fehlt auf der Anmeldeseite

Ursache
Der Link setzt vollständig konfiguriertes SMTP voraus und aktive Passwort-Anmeldung. Ohne Versandweg wäre er wirkungslos, deshalb wird er ausgeblendet.
Behebung
Einstellungen → Anmeldung & E-Mail → E-Mail-Versand: aktivieren, Host, Port und Absender eintragen. Prüfen, dass unter Benutzer & Zugriff die Passwort-Anmeldung nicht abgeschaltet ist.

SSO bricht ab mit einer Meldung zur redirect_uri

Ursache
Die von der App gesendete Adresse weicht von der beim Identitätsanbieter registrierten ab. Ohne gesetzte öffentliche App-URL rät die App die Adresse aus der Anfrage und liegt hinter einem Proxy fast immer daneben.
Behebung
Einstellungen → Marke → Öffentliche Adresse auf die echte, von außen erreichbare HTTPS-Adresse setzen. Beim Anbieter exakt <App-URL>/api/auth/oidc/callback registrieren — zeichengenau, auch beim abschließenden Schrägstrich.

SSO-Knopf erscheint gar nicht

Ursache
SSO muss beides sein: über Umgebung oder Adminfeld konfiguriert und im Adminbereich eingeschaltet.
Behebung
Client-ID und Secret prüfen, dann Benutzer & Zugriff → Anmeldearten.

Anmeldung wird abgelehnt, obwohl das Konto beim Anbieter existiert

Ursache
Eine gesetzte Mandanten-ID beschränkt die Anmeldung: der tid-Anspruch im Token muss übereinstimmen. Gastkonten aus anderen Mandanten fallen dadurch heraus.
Behebung
Mandanten-ID prüfen oder für mandantenübergreifende Anmeldung leer lassen und die Endpunkte per OIDC_AUTHORIZE_URL / OIDC_TOKEN_URL vorgeben.

Passwort des Administrators vergessen, kein SMTP eingerichtet

Ursache
Ohne Versandweg gibt es keinen Self-Service-Reset. Den Passwort-Hash in users.json zu löschen hilft nicht — verifyPassword() lehnt ein Konto ohne Hash grundsätzlich ab, das Konto wäre danach endgültig gesperrt.
Behebung
Nur mit Zugriff auf das Datenverzeichnis. Container stoppen, data/users.json sichern, dann den Eintrag des Administratorkontos vollständig aus der Liste entfernen. Bleibt danach kein Konto mit der Rolle admin übrig, meldet /api/setup wieder needsSetup und die Ersteinrichtung erscheint beim nächsten Aufruf.

Modelle & Antworten

Die Anwendung übersetzt Fehler der Modell-Endpunkte in Klartext. Die folgende Tabelle ordnet jeder Meldung die technische Ursache zu.

Meldung im ChatDahinter stecktPrüfen
„Der KI-Server ist nicht erreichbar.“ fetch failed, ECONNREFUSED, DNS-Fehler Läuft Ollama? Stimmt die Basis-URL? Aus dem Container muss es host.docker.internal sein, nicht localhost.
„Dieses Modell steht gerade nicht zur Verfügung.“ 404 / model … not found Modell auf dem Server vorhanden? Über Modelle laden nachziehen. Nach dem Entfernen eines Modells kann ein Standardmodell ins Leere zeigen.
„Der Zugang zum KI-Dienst wurde abgelehnt.“ 401 / 403, ungültiger API-Schlüssel Schlüssel unter Anbieter & Endpunkte erneuern. Schlüssel werden verschlüsselt gespeichert und nie an den Browser gegeben.
„Gerade sind zu viele Anfragen unterwegs.“ 429 Kontingent des Anbieters, oder zu viele gleichzeitige Nutzer auf einer GPU.
„Die Antwort hat zu lange gedauert.“ Zeitüberschreitung Erstes Laden eines großen Modells dauert. keep_alive erhöhen, damit es geladen bleibt.
„Diese Unterhaltung ist zu lang geworden.“ Kontextfenster überschritten Neuen Chat beginnen. Angehängte Dokumente und Wissenstreffer verbrauchen zusätzlich Kontext.
„Dem Server ist der Speicher ausgegangen.“ Grafikspeicher erschöpft Kleineres Modell, oder OLLAMA_MAX_LOADED_MODELS=1 und OLLAMA_NUM_PARALLEL=1 auf dem Ollama-Host.
„Der KI-Dienst hat einen Fehler gemeldet.“ 5xx Logs des Modellservers ansehen.
Unter jeder dieser Meldungen steht kleingedruckt „Technisch: …“ mit dem Originaltext. Genau die Zeile gehört in eine Fehlermeldung an den Support.

Modellauswahl ist leer

Ursache
Kein Anbieter eingetragen oder er antwortet nicht.
Behebung
Einstellungen → Modelle → Anbieter & Endpunkte. Erreichbarkeit direkt gegenprüfen: curl http://<host>:11434/api/tags.

Funktionen

Websuche liefert nichts

Ursache
Kein Suchanbieter mit Schlüssel aktiv. Verwendet wird der erste aktivierte Anbieter, der einen Schlüssel hat.
Behebung
Einstellungen → Integrationen → Suchanbieter. Zusätzlich muss unter Standardmodelle ein Modell für die Suchbegriff-Konstruktion hinterlegt sein.

Ein Nutzer sieht seine Wissens-Kategorien nicht

Ursache
Kategorien sind Berechtigungen, und die Grundeinstellung ist „alles verboten“. Ohne Zuweisung ist nichts sichtbar.
Behebung
Benutzer & Zugriff → Kategorie-Matrix beim jeweiligen Konto ankreuzen. Administratoren sehen implizit alles, weshalb der Fehler beim Testen mit einem Adminkonto unsichtbar bleibt.

Antworten belegen keine Quellen

Ursache
Die Wissensdatenbank ist im Chat abgeschaltet, oder es passt kein Dokument zur Frage.
Behebung
Den Bücherstapel neben dem Eingabefeld einschalten — aktiv zeigt er die Beschriftung „Wissen“.

Gäste können nicht chatten

Ursache
Gastzugang aus, oder kein Gastmodell hinterlegt. Für Gäste wird das Modell serverseitig erzwungen.
Behebung
Benutzer & Zugriff → Gastzugang einschalten und ein Modell wählen.

Daten

Nach dem Update sind Konten und Einstellungen weg

Ursache
Das Datenvolume wurde nicht eingebunden oder wurde entfernt. docker compose down -v löscht Volumes mit.
Behebung
Zum Stoppen docker compose down ohne -v verwenden. docker volume ls zeigt, ob openchatbox-data noch existiert.

Chats verschwinden oder springen zurück

Ursache
Chats sind client-autoritativ: der Browser schiebt den gesamten Satz zeitverzögert zum Server. Zwei gleichzeitig offene Tabs desselben Kontos können sich gegenseitig überschreiben.
Behebung
Pro Konto einen Tab verwenden. Erscheint unten der Hinweis „Serverspeicherung fehlgeschlagen“, ist der Schreibvorgang gescheitert — Plattenplatz und Schreibrechte auf data/ prüfen.

Inkognito-Chats sind nach dem Neuladen weg

Ursache
Kein Fehler, sondern der Zweck. Temporäre Chats werden nie zum Server geschickt.
Behebung
Vor dem Verlassen im Geist-Menü „Chat behalten & speichern“ wählen.

Bekanntes Problem: npm run lint läuft nicht. Das Skript ruft next lint auf, das es in Next 16 nicht mehr gibt; zudem liegt weder eine eslint.config.* noch eine .eslintrc im Projekt, und ESLint ist keine Abhängigkeit. Als Qualitätsschranke dienen derzeit npm run typecheck, npm run build und npm test.

Versionierung und Release

Einzige Quelle der Wahrheit ist lib/version.ts mit APP_VERSION und CHANGELOG (neuester Eintrag zuerst). Der Bereich Über OpenChatbox rendert diesen Änderungsverlauf; der Benachrichtigungspunkt richtet sich nach der obersten Version.

Für ein Release APP_VERSION erhöhen, einen neuen obersten Changelog-Eintrag schreiben, dann npm run release. Das Skript setzt und schiebt den Tag vX.Y.Z und verwendet den Changelog-Eintrag wörtlich als Release-Text, damit Releases-Seite und Oberfläche nicht auseinanderlaufen.

Konventionen

  • Oberfläche und Änderungsverlauf sind deutsch; README und Code-Kommentare englisch.
  • data/ und .env gehören niemals ins Repository.
  • Keine neuen REST-Routen für chat-nahe Daten — siehe Chat-Synchronisation.
